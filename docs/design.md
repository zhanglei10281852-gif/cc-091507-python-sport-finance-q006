# 分润内核设计说明

本文档说明事件、分录、规则版本、账期锁定与更正、确定性重放之间的关系。
领域背景见 `docs/domain.md`，公开枚举见 `reference/domain.json`。

## 1. 事件溯源与时间

一切业务事实都是**只追加的事件**（`src/profitshare/events.py`）：

| 事件 | 含义 |
| --- | --- |
| `rule_version_published` | 发布一个规则版本 |
| `package_purchased` | 课包成交（形成待履约负债） |
| `session_scheduled` | 团课排课 |
| `substitute` | 教练请假、替补登记（公开事件类型） |
| `class_booked` | 会员预约，占用课包课节 |
| `checked_in` | 签到核销（公开事件类型，必须关联 booking） |
| `referral` | 转介绍关系（公开事件类型） |
| `refund` | 退款（公开事件类型，可指定冲回的核销） |
| `bad_debt` | 坏账 |
| `package_transferred` | 课包转让 |
| `month_settled` | 月结锁定 |
| `settlement_correction` | 月结更正（公开事件类型，必须带理由） |

每个事件带三个关键时间/标识：

- `event_id`：全局稳定标识。命令默认用业务自然键派生
  （如 `checkin:{booking_id}`、`settle:{period}`），因此同一条命令
  因网络重试发送多次，效果与一次完全相同；
- `service_time`：业务**真实发生时间**。规则版本归属、账期归属都以它为准；
- `recorded_at`：系统**接收时间**。月结后的补录允许接收时间晚于账期，
  但必须通过更正批次入账。

## 2. 分录（Entry）

`materialize(events)` 把事件重放成不可变分录（`src/profitshare/engine.py`）。
每条分录包含：收款方类型（coach/sales/store）与 id、金额（整数分，带正负号）、
币种、来源、账期、规则版本快照、关联原记录、所属批次号、反向链。

一次签到核销产生：

1. 门店确认收入（store +）；
2. 实际授课教练提成（coach +）——替补生效时是替补教练；
3. 若该会员由转介绍而来且奖励设定为首次核销兑现，再产生销售拉新奖励（sales +），
   每位被介绍会员**至多一次**。

金额一律整数分；提成按基点（万分之一）四舍五入。不同币种全程分开汇总。

## 3. 规则版本

`RuleVersion(version_id, effective_from, coach_bps, referral_reward_cents, ...)`
按生效日发布。取版本规则 = `effective_from <= 服务发生日` 中最新的版本，
分录落账时把 `version_id` 快照在分录上。因此：

- 3 月补录 1 月的签到，仍按 1 月规则计提成、归 1 月账期；
- 3 月发布新规则，重跑 1 月批次结果不变。

规则开关：`clawback_consumed_refund`（已核销课节退款是否追回授课提成）、
`referral_clawback_on_bad_debt`（坏账是否追回拉新奖励）、
`referral_on_checkin`（拉新奖励是首次核销兑现还是转介绍即时兑现）。

## 4. 退款与坏账：只追加反向分录

退款/坏账**永不修改或删除**历史分录，而是追加金额相反、
`reversal_of` 指向原分录的反向分录：

- 反向分录入账在退款/坏账**发生的当期**，已锁定账期的批次原样不动；
- 退款时已核销课节的收入始终退回；授课提成是否追回由当时生效规则决定；
- 拉新奖励只在会员已不存在任何有效核销（拉新成立基础整体失效）时追回，
  避免“退一节课就争一笔奖励”；
- 同一原分录只能被冲回一次；退款课包必须与核销课包一致；
- 未核销课节的退款只减少履约负债，不产生损益分录；
- 坏账冲回该课包全部尚未冲回的核销链路，课包随后不得再预约；
  课包曾转让时，历任持有人的即时拉新奖励也会被一并检查追回。

## 5. 课包转让

`package_transferred` 只移动未履约负债（剩余课节、当前持有人/门店）：

- 历史核销分录一律不动——收入责任留在真实服务发生处；
- 转介绍关系不随课包转移，受让会员的核销不再触发拉新奖励；
- 转让后新发生的核销按新门店、实际上课教练记账。

## 6. 月结、锁定与更正批次

`month_settled` 把该账期所有未入批次的分录封进锁定批次：

```
JS202601-AB12CD34        # 锁定批次：JS + 账期 + 分录内容 sha256 前 8 位
JS202601-AB12CD34-C1     # 更正批次：必须带理由
JS202601-AB12CD34-C2
```

锁定后：

- 锁定期内的新预约、签到、退款、坏账一律拒绝（422）；
- 只能用 `settlement_correction` 追加，且**理由必填**，支持三种内容：
  - `lines`：手工调整分录（必须有 store_id；反向调整须指向真实历史分录、金额为负）；
  - `late_checkins`：月结后补录签到，**必须关联锁定期前已存在的原预约**；
  - `late_bookings`：连预约都是纸质单时，补建预约并核销；
- 追加更正后，原锁定批次状态变 `corrected`，但其内容与编号永不变。

## 7. 确定性重放

- entry_id 由 `事件 id + 事件内序号 + 收款方` 派生；
- 锁定批次号只取决于该账期封批次时的分录集合（校验和计算时忽略
  批次号这一结算时回填的派生字段）；
- 更正批次号由锁定批次号与更正序号派生；
- 投影不依赖 wall-clock、字典插入顺序之外的任何外部状态，
  核销/更正分录入批次前统一按 entry_id 排序。

因此财务重跑同一结算批次：分录、金额、批次编号全部稳定。
`GET /batches/{no}/verify` 会从零重放事件流并复算校验和。

## 8. 查询

- 个人台账 `/people/{id}/statement`：逐笔列出来源、正负金额、币种、
  规则版本、关联原记录、所属批次与理由；按币种给出收入/扣减/净额；
- 门店对比 `/stores/comparison`：按币种给出毛收入、净收入、
  提成与拉新支出、留存、留存率，以及人均留存、单核销场次收入等人效指标。
